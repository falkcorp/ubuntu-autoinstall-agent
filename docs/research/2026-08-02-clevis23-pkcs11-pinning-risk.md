# clevis 23 / pkcs11 pin on Ubuntu 26.04: pinning design, and why the `openssl-provider-legacy` collision turned out not to exist

**Status: RESOLVED (2026-08-02). The `openssl-provider-legacy` collision DOES
NOT OCCUR** — it was an artifact of reading the dependency metadata of the
wrong build of clevis 23. Measured end to end in a stock Ubuntu 26.04
container; see [Resolution](#resolution). The flag remains off by default
because it changes apt state and should be opted into per host, not because the
risk is open.

## Why any of this exists

The clevis **pkcs11 pin** lets a YubiKey PIV applet act as a LUKS unlock
factor. It does not exist in the clevis Ubuntu 26.04 ships.

Measured on len-serv-003 (Ubuntu 26.04 "resolute"):

| Fact | Evidence |
|---|---|
| 26.04 ships clevis `20-1ubuntu2` from `resolute/universe` | `apt-cache madison clevis` |
| clevis 20 has no pkcs11 pin | `clevis luks bind -d <dev> pkcs11 '{…}'` → `'pkcs11' is not a valid pin!`, rc=2 |
| No pkcs11 files in any clevis package | `dpkg -L` across all installed clevis packages: zero hits |
| `resolute-backports` is enabled and indexed, but does NOT carry clevis | `apt-cache madison clevis` shows only `20-1ubuntu2` |
| Ubuntu 26.10 ("Stonking Stingray") ships clevis `23-1build1`, which has the pin | `dpkg -c` on the 26.10 debs |

So the only route to the pin on a 26.04 host is to pull clevis 23 out of the
26.10 pocket.

## Where the pin's pieces live in clevis 23

Verified by `dpkg -c` on the actual 26.10 debs. **There is no separate
`clevis-pkcs11` package** — this is the single most likely wrong assumption:

| Package | pkcs11 contents |
|---|---|
| `clevis` | `clevis-encrypt-pkcs11`, `clevis-decrypt-pkcs11`, `clevis-pkcs11-afunix-socket-unlock`, `clevis-pkcs11-common` |
| `clevis-dracut` | `/usr/lib/dracut/modules.d/50clevis-pin-pkcs11/` (`module-setup.sh`, `clevis-pkcs11-hook.sh`, `clevis-pkcs11-prehook.sh`) |
| `clevis-systemd` | `clevis-luks-pkcs11-askpass.service` + `.socket`, `/usr/libexec/clevis-luks-pkcs11-askpass`, `clevis-luks-pkcs11-askpin` |

Consequence: the pin needs `clevis` on the **live** host (where `clevis luks
bind` runs — the LUKS mapper is not visible in the chroot) *and*
`clevis-dracut` + `clevis-systemd` in the **target**, or the keyslot exists and
never unlocks at boot.

## Why the pin file has to be narrow

The clevis binaries are lockstep-versioned, so one package cannot be pinned
alone — apt would find it unresolvable:

```
clevis-luks    Depends: clevis (= 23-1build1)
clevis-systemd Depends: clevis-luks (= 23-1build1)
clevis-dracut  Depends: clevis-systemd (= 23-1build1), dracut-core (>= 110~)
clevis-tpm2    Depends: clevis (= 23-1build1)
```

And an apt source added with no pin at all sits at the default priority 500.
Because *every* 26.10 package outranks its 26.04 twin by version, that would
make the entire base system dist-upgradable to 26.10 on the next
`apt full-upgrade`. Hence the generated file has two blocks: an explicit
allowlist at 501, and a `Package: *` catch-all for the same release at -1.

Generated by `packages::clevis23_preferences_content` (pure function, unit
tested), written to `/etc/apt/preferences.d/99-uaa-clevis23-pkcs11` on both the
live host and the target.

## Dependency analysis (all satisfied except one)

`clevis 23-1build1 Depends: libc6 (>= 2.34), libjansson4 (>= 2.14), libjose0
(>= 10), libssl4 (>= 4.0.0), cracklib-runtime, curl, jose, libpwquality-tools,
luksmeta`; `Recommends: cryptsetup-bin, opensc`.

Everything except `libssl4` is already satisfied on 26.04: libjansson4 2.14,
libjose0 14, curl, jose, luksmeta, cracklib-runtime, libpwquality-tools, jq,
cryptsetup-bin, tpm2-tools, dracut-core 110-11 (`>= 110~`), dracut-network.

`libssl4` does not exist in 26.04 (which has `libssl3t64 3.5.5`). The 26.10
`libssl4 4.0.1-1ubuntu1 Depends: libc6 (>= 2.38), libzstd1 (>= 1.5.5), zlib1g
(>= 1:1.1.4), openssl-provider-legacy`. 26.04 satisfies the first three —
libc6 **2.43**, libzstd1 **1.5.7**, zlib1g **1.3.1** — so **there is no glibc
cascade**. libssl4 ships `libssl.so.4` / `libcrypto.so.4`, distinct sonames
from the installed `.so.3`, so it **co-installs**.

`opensc` and `pcscd` are available in 26.04 universe but not installed, and
`clevis` only *Recommends* opensc. They are installed at their stock 26.04
versions and are deliberately **excluded** from the pin.

## Resolution: release pocket vs `-proposed`

**The non-obvious fact, which someone will otherwise rediscover the hard way:
26.10 carries TWO builds of clevis 23, and they have different OpenSSL
dependencies.**

| Build | Pocket | Linked against | Depends |
|---|---|---|---|
| `23-1` | `stonking` (**release**) | OpenSSL 3 | satisfied by 26.04's own `libssl3t64` |
| `23-1build1` | `stonking-proposed` | OpenSSL 4 | `libssl4 (>= 4.0.0)` → 26.10 `openssl-provider-legacy` |

The original dependency analysis below read `23-1build1` — the **proposed**
build. That is where `Depends: libssl4` comes from, and therefore where the
entire `openssl-provider-legacy` displacement scenario comes from. It does not
apply to the build we actually install.

`Suites: stonking` names the release pocket only, so the candidate resolves to
`23-1` and `libssl4` is never a consideration.

### Measured on stock Ubuntu 26.04

| Observation | Result |
|---|---|
| `clevis`, `clevis-luks`, `clevis-tpm2` | installed at `23-1` |
| `libssl4` | **never pulled** — absent |
| `openssl-provider-legacy` | **unchanged** at the 26.04 `3.5.5-1ubuntu3.2` |
| `libssl3t64` | intact at `3.5.5-1ubuntu3.3` |
| `opensc` + `opensc-pkcs11` | `0.27.0~rc1-1`, auto-installed via clevis 23's *Recommends* |
| `/usr/bin/clevis-encrypt-pkcs11`, `clevis-decrypt-pkcs11` | present |
| `openssl version`, `openssl list -providers`, `openssl dgst`, a TLS handshake, `apt update` | all OK |

And, separately measured: on stock 26.04 the legacy provider is **not active**
anyway. `openssl list -providers` shows only `default`, and `/etc/ssl/openssl.cnf`
has `# activate = 1` commented out. So even the displacement scenario, had it
been real, would have been inert — which is precisely what check (2) and (3) of
[Settling it](#settling-it) were written to determine.

### What changed in the code

- `CLEVIS23_PINNED_PACKAGES` no longer lists `libssl4` or
  `openssl-provider-legacy`. Keeping them would have been harmless but
  misleading — it would imply the OpenSSL 4 path is expected.
- `sources_never_enable_the_proposed_pocket` asserts the generated deb822
  sources file contains no `proposed`. That single word is the difference
  between a clean install and an OpenSSL 4 migration, and it is exactly the kind
  of "get the newest build" edit a future author would make in good faith.
- `opensc` is still installed explicitly. It arrives as a *Recommends* of
  clevis 23, so this is belt-and-braces: it survives `--no-install-recommends`
  and makes the dependency explicit rather than incidental. `pcscd` is
  recommended by nothing and **must** stay explicit.

## HISTORICAL: the collision as originally analysed

*Everything from here to the end of this section describes `23-1build1` from
`-proposed` and is retained only so the reasoning is auditable. It does not
describe what the installer does.*

### The collision

`openssl-provider-legacy` is a **single package name**. It is installed at
`3.5.5-1ubuntu3.3` (part of the 26.04 OpenSSL 3.5 stack), and the 26.10 version
`4.0.1-1ubuntu1` `Depends: libssl4 (>= 4.0.0)`. Two versions of one package
cannot coexist.

So pulling `libssl4` **displaces** the legacy provider that the installed
OpenSSL 3.5 stack currently uses. The soname argument that makes libssl4 safe
does **not** extend to this package: it is one name, one installed version, and
the newer one is built against `libcrypto.so.4`.

What is genuinely unknown from here is whether anything on the host *uses* the
legacy provider. Stock Ubuntu installs `openssl-provider-legacy` without
activating it in `openssl.cnf`, in which case the displacement is inert. If it
*is* activated, the swap could break legacy-algorithm consumers (older PKCS#12
bundles, MD4/RC4-era paths) with a runtime error rather than an install-time
one — which is the bad kind of failure for a machine that has to boot
unattended.

**Assessment / the call:** unresolved, mitigated by being off by default, and
gated. Not green. The co-install of `libssl.so.4` alongside `.so.3` is proven
safe by soname; the single-name displacement of the provider package is not,
and it cannot be verified from the repo.

### Settling it (historical — these checks were run, see Resolution)

Run these on a **scratch** 26.04 host — never on the fleet. `rdepends` alone is
not the discriminator; the question is whether the provider is *activated*, not
whether it is installed:

```sh
# 1. What installed packages actually depend on it?
apt-cache rdepends --installed openssl-provider-legacy

# 2. Is the legacy provider loaded at runtime, or only present on disk?
openssl list -providers

# 3. Is it activated in config, or is the section inert/commented?
grep -n -A5 -i 'legacy\|\[provider_sect\]\|activate' /etc/ssl/openssl.cnf
```

Then dry-run the actual displacement and read what apt proposes to remove:

```sh
apt-get -s install -y clevis clevis-luks clevis-dracut clevis-systemd clevis-tpm2
```

If (1) shows only the OpenSSL stack itself, (2) does not list `legacy` among
loaded providers, and (3) shows no active legacy section, the displacement is
inert and the flag can be enabled on a host. If any of the three says
otherwise, the correct answer is to stop pinning and instead build clevis 23
against 26.04's OpenSSL 3.5, or wait for a real backport.

## What the flag does


`InstallationConfig.clevis_pkcs11_pin` — bool, `#[serde(default)]`, **false**,
and `skip_serializing_if` so an off flag never even appears in a resolved
config (rollback safety, same reasoning as `applications`). Profile-lowered
hosts always get `false`; the flag is currently authorable only in raw
per-host `InstallationConfig` YAML.

When true:

1. `packages::clevis23_apt_config_commands` writes the deb822 source
   (`Components: main universe` — clevis is in universe, libssl4 in main;
   dropping either makes the whole thing a silent no-op) and the narrow pin,
   **before** `apt update` on both the live host and inside the target chroot.
   Ordering is load-bearing: after `apt update`, the pocket is unindexed and
   the install silently resolves clevis 20.
2. `opensc` + `pcscd` are added to both package sets, unpinned.

When false, not a single command changes — asserted by
`clevis_pkcs11_pin_defaults_off_and_changes_nothing` against the verbatim
pre-change apt line.

## Known gaps

- ~~Nothing yet *uses* the pin~~ — **closed.** `UnlockPin::Pkcs11` shares now
  emit through `build_clevis_policy_from_tree` at arbitrary nesting depth, and
  `SssPolicy::fleet_three_group` builds the settled fleet policy. See
  `docs/research/2026-08-02-pkcs11-share-binding-hazard.md`, which carries the
  **mandatory** post-bind verification matrix — binding this policy needs all
  three tokens plugged in at once, which is exactly when clevis's `head -1`
  public-key lookup can silently encrypt every share to the same token.
- The suite name `stonking` is a single `const` in `packages.rs`
  (`CLEVIS23_SUITE`); if 26.10's suite string turns out to differ, that is a
  one-line fix.
- `InitramfsTools` targets do not get `clevis-dracut`/`clevis-systemd`, so the
  pkcs11 pin is effectively Dracut-only. Every real host here is Dracut.
- The `Package: *` / `Pin-Priority: -1` catch-all means any 26.10-only
  transitive dependency that is *not* on the allowlist makes `apt install` fail
  outright rather than half-install. That is deliberate: an install-time failure
  is recoverable, a machine that boots without an unlock factor is not.
- `clevis_pkcs11_pin` is OR-ed into `needs_clevis` in `system_setup.rs`, so a
  Tang-less `plain-luks` host with the flag on still gets the clevis packages.
  Without that term the flag would pin the pocket and install `opensc`/`pcscd`
  while installing no clevis at all — a silent success with no unlock factor.
